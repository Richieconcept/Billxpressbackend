Overview

The Vendor API is designed for approved BillXpress vendors who want to resell services from their own website, mobile app, agent system, or backend.

Vendor requests are authenticated with a vendor API key. The API uses the vendor wallet balance, applies vendor pricing, records transactions, and returns references that vendors can store in their own system.

This page documents the vendor-facing API contract. These routes should be implemented under /api/v1/vendor and should not require customer JWT tokens or transaction PINs.

Quickstart

1
Get approved
Create a BillXpress account and request vendor approval from an admin.
2
Receive API key
After approval, the admin dashboard returns a unique vendor API key.
3
Fund wallet
Keep enough balance in the vendor wallet before placing orders.
4
Start requests
Send your API key in the Authorization header and store every reference.
Minimal Request 
curl -X GET "https://billxpressbackend-production.up.railway.app/api/v1/vendor/me" \
  -H "Authorization: YOUR_VENDOR_API_KEY"

Authentication

Send the vendor API key directly in the Authorization header. Do not prefix vendor keys with Bearer.

Correct 
Authorization: bxp_vendor_live_xxxxxxxxxxxxx
Incorrect 
Authorization: Bearer bxp_vendor_live_xxxxxxxxxxxxx

Authentication Rules

Rule Requirement
Account role The account must have role: "vendor".
Vendor status The account must have isVendorActive: true.
Header Use Authorization: YOUR_VENDOR_API_KEY.
Secret handling Keep API keys on backend servers only. Do not expose them in browser JavaScript or mobile app bundles.

Response Format

Public responses should use one predictable envelope so vendors can integrate once and handle all services consistently.

Success 
{
  "success": true,
  "message": "Request completed successfully",
  "data": {}
}
Error 
{
  "success": false,
  "message": "Insufficient wallet balance",
  "code": "INSUFFICIENT_BALANCE"

Wallet

GET /api/v1/vendor/wallet
Read balance

Returns the vendor wallet balance. Purchases are debited from this wallet.

GET /api/v1/vendor/transactions?limit=50
Transaction history

Returns recent transactions for the vendor account. Use this for reconciliation and customer support.

Query Type Description
limit number Optional. Maximum number of transactions to return. Recommended max is 100.
service string Optional. Filter by airtime, data, or social_growth.
status string Optional. Filter by successful, failed, or reversed.

References And Idempotency

Vendors should send a unique customerReference for every purchase. BillXpress should store it in transaction metadata and prevent duplicate charges for repeated requests with the same reference.

Reference Generated By Purpose
reference BillXpress Official transaction reference for wallet debit and support.
customerReference Vendor Vendor's own order ID for reconciliation and duplicate protection.
providerReference Provider External provider ID returned by data, airtime, or social growth provider.

Webhooks

Webhooks notify a vendor backend when an order succeeds, fails, or is reversed. This is useful when the vendor's own checkout cannot wait for provider completion.

Rate Limits

Vendor API traffic is rate limited to protect service reliability. The current limit is 120 requests per minute per endpoint/IP.

Rate Limit Response 
{
  "success": false,
  "message": "Too many vendor API requests, please try again shortly",
  "code": "RATE_LIMITED",
  "retryAfterSeconds": 30
}

Error Codes

HTTP Code Meaning
401 INVALID_API_KEY The vendor API key is missing, invalid, inactive, or belongs to a non-vendor account.
400 VALIDATION_ERROR A required field is missing or invalid.
400 INSUFFICIENT_BALANCE The vendor wallet balance is too low for the requested purchase.
409 DUPLICATE_REFERENCE The customerReference has already been used for this vendor.
503 SERVICE_UNAVAILABLE The selected service or provider is temporarily unavailable.
429 RATE_LIMITED The vendor made too many requests in a short period. Wait for retryAfterSeconds.

Security Guidelines

Treat every vendor API key like a password. A leaked key can spend the vendor's wallet balance.
Do Do Not
Store the API key in backend environment variables. Do not put the API key inside frontend JavaScript.
Use HTTPS for all requests. Do not send API requests over plain HTTP in production.
Send a unique customerReference for every purchase. Do not retry purchase requests without idempotency protection.
Log BillXpress references for support and reconciliation. Do not expose provider raw responses to end customers.
